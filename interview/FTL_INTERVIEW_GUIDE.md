# FTL Reliability Simulator: Technical Interview & Engineering Guide

This document provides rigorous, engineering-grade answers to the 25 core FTL architectural and reliability questions explored and validated in this project.

---

### 1. Why can't NAND overwrite a page in place?
NAND flash memory cells are organized into floating gate or charge trap transistors. Programming a cell injects electrons through the oxide insulator, transitioning it from an erased state (logical `1`) to a programmed state (logical `0`). Once programmed, individual cells cannot selectively remove trapped charge; pulling electrons back out requires applying a high reverse voltage across the entire bulk p-well substrate. This high voltage physically encompasses an entire **NAND block** (comprising 128–512 pages). Consequently, overwriting an individual page in place is physically impossible without erasing the entire enclosing block, necessitating out-of-place writes and an active Flash Translation Layer (FTL).

### 2. Why does FTL need logical-to-physical mapping?
Host operating systems and file systems address storage devices using contiguous, linearly indexed Logical Block Addresses (LBAs) with in-place overwrite semantics (POSIX/block layer). Because NAND cannot overwrite in place, incoming writes must be redirected to freshly erased physical pages (PPAs). The FTL maintains a dynamic **Logical-to-Physical (L2P)** mapping table in controller SRAM/DRAM to translate host LBAs to their current physical locations (channel, die, plane, block, page).

### 3. What causes write amplification?
Write Amplification Factor (WAF) is defined as:
$$\text{WAF} = \frac{\text{Total Bytes Written to Physical NAND}}{\text{Total Bytes Written by Host}}$$
When an LBA is updated out-of-place, its old physical page is marked **Invalid**. Over time, blocks accumulate a mix of valid and invalid pages. To reclaim storage space, Garbage Collection (GC) must select victim blocks, read out all remaining **Valid** pages, copy (relocate) them to a clean allocation block, and then erase the victim block. The extra physical writes generated by valid page relocation cause $\text{WAF} > 1.0$.

### 4. How does over-provisioning affect GC?
Over-provisioning (OP) is reserved physical NAND capacity invisible to the host operating system:
$$\text{OP\%} = \frac{\text{Physical Capacity} - \text{User Capacity}}{\text{User Capacity}} \times 100\%$$
Higher OP provides a larger pool of spare blocks for the FTL allocator. As OP increases, average block invalidation density increases before GC is forced to trigger. Victim blocks selected by GC therefore contain significantly higher fractions of invalid pages and fewer valid pages to relocate. Under uniform random write workloads, increasing OP from 7% to 28% can reduce WAF from $\sim 3.5$ down to $<1.8$, directly reducing NAND write wear and improving sustained write throughput.

### 5. What happens when a block has valid and invalid pages?
A block containing both valid and invalid pages is in an active, fragmented state. The invalid pages represent obsolete data versions whose LBAs have either been overwritten or trimmed. Because the block cannot be erased while valid pages reside on it, it occupies physical capacity without being reusable. When selected as a GC victim, the FTL must execute a read-modify-relocate cycle for every valid page before executing a block erase command.

### 6. How do you select a GC victim?
Two primary policies are implemented:
1. **Greedy Policy**: Computes the number of invalid pages per block and selects the block with the maximum invalid count (minimum valid count). This minimizes valid page relocation overhead in the immediate cycle.
2. **Cost-Benefit Policy**: Evaluates $\text{Metric} = \frac{\text{Age} \times (1 - u)}{2u}$, where $u$ is block utilization (valid fraction) and $\text{Age}$ is the elapsed time since the last write on that block. This prevents cold blocks from remaining untouched indefinitely while prioritizing blocks that yield maximum free space per write.

### 7. Why can aggressive GC hurt latency?
Flash erase operations take orders of magnitude longer than reads or writes ($t_{\text{ERASE}} \approx 3.5\text{ms}$ vs $t_{\text{PROG}} \approx 600\mu\text{s}$ vs $t_{\text{READ}} \approx 50\mu\text{s}$). During synchronous or emergency foreground GC, host I/O requests queue behind valid-page copy reads, program commands, and multi-millisecond block erases across shared channels and dies. This contention leads to severe 99.9th and 99.99th percentile (tail) read and write latency spikes.

### 8. Static vs dynamic wear leveling?
- **Dynamic Wear Leveling**: Directs incoming host writes to the least-worn available free blocks (blocks with the lowest erase counts). This evens out wear among actively updated "hot" data blocks.
- **Static Wear Leveling**: Addresses "cold" data that is written once and never updated (e.g., OS binaries). Cold data permanently occupies physical blocks whose erase count remains frozen while hot blocks cycle rapidly. When the spread $(\max(\text{erase}) - \min(\text{erase}))$ exceeds a threshold (e.g., 8–16 erases), the static wear leveler proactively reads the cold data and relocates it to high-erase blocks, freeing up the low-erase block for active host recycling.

### 9. Why is a reverse mapping useful?
The Physical-to-Logical (P2L) reverse map records the owning LBA for every physical page:
1. **Garbage Collection**: When reading a valid page from a victim block, the FTL must look up its LBA to verify if the page is still active in the primary L2P map and update L2P to point to the new relocation target.
2. **Metadata Integrity & Invariant Checking**: Enables bi-directional verification ($\text{L2P}[L] = P \iff \text{P2L}[P] = L$) to detect orphaned physical pages, multi-owner corruptions, and memory bit flips.
3. **Power-Loss Recovery**: When rebuilding volatile L2P tables from flash during recovery, scanning the out-of-band (OOB) spare area containing P2L metadata reconstructs the mapping table without requiring an external database.

### 10. What is stale-read corruption?
Stale-read corruption occurs when a host read request for LBA $L$ returns data from an obsolete, previous physical page $P_{\text{old}}$ instead of the most recently written data $P_{\text{new}}$. This typically arises if the storage system crashes before in-memory or on-flash mapping metadata is persisted, causing a recovered controller to point back to the pre-crash physical location.

### 11. How could one physical page become owned by two LBAs?
This critical defect occurs when reverse mapping or forward mapping updates are executed non-atomically. For example:
1. LBA $A$ is written to physical page $P_1$.
2. GC relocates $P_1$ to $P_2$, but the controller crashes halfway through updating L2P.
3. Upon restart, a corrupted recovery routine maps new write LBA $B$ to $P_1$ (believing $P_1$ was freed), while $A$'s stale mapping still references $P_1$. Both LBAs $A$ and $B$ now claim ownership of $P_1$, causing silent data corruption whenever either LBA is accessed.

### 12. Why are acknowledged writes a special durability boundary?
When an NVMe controller posts a Completion Queue Entry (CQE) with status `SUCCESS` to the host CPU, it provides an irrevocable contract under the POSIX/NVMe specification: **the acknowledged data must survive any subsequent sudden power loss**. Any write acknowledged to the host that fails to survive a restart or returns unwritten data is an unrecoverable **Durability Violation** and data loss event.

### 13. What exactly failed in the metadata-ordering defect?
In vulnerable recovery mode:
```text
Host Write Pipeline:
1. Program Data to NAND Page (PPA_new)
2. Return Host ACK (Completion Queue Entry)
3. Update Volatile In-Memory L2P Table
4. (Periodic / Delayed) Commit L2P Checkpoint to NAND
```
If sudden power loss occurs at crash point `AFTER_ACK` (or between 2 and 4):
The host has received confirmation that the data is durable. However, the updated mapping was never persisted to non-volatile storage. Upon reboot, the FTL recovers from the stale pre-crash checkpoint. The host's acknowledged write is completely lost, violating the durability invariant.

### 14. Why did write-ahead logging (WAL) fix it?
Write-Ahead Logging enforces strict transactional ordering:
```text
Host Write Pipeline:
1. Program Data to NAND Page (PPA_new)
2. Append Mapping Intent Record to WAL Log with CRC: {seq, LBA, PPA_new, crc}
3. Flush / Commit WAL Entry to Flash
4. Update Volatile In-Memory L2P Table
5. Return Host ACK
```
No host write is acknowledged until both the user data AND the WAL mapping record are guaranteed to be durable on physical media. Upon recovery, the FTL loads the baseline checkpoint and replays all subsequent uncorrupted WAL records in sequence, perfectly restoring L2P mappings up to the exact point of host acknowledgement.

### 15. What if the system crashes while writing the WAL?
If a sudden power loss occurs while programming the WAL entry itself, a **torn write** results. The WAL entry will have incomplete bits, erased flash tail padding (`0xFF`), or an invalid CRC checksum. During recovery replay:
1. The FTL verifies the 32-bit CRC of each WAL record.
2. Upon encountering a torn or corrupted record, replay halts cleanly.
3. Because this write was never acknowledged to the host (the crash occurred before Step 5), dropping the torn record preserves strict POSIX and NVMe consistency without violating durability guarantees.

### 16. Why checksum checkpoints?
Checkpoints serialize large in-memory L2P tables across multiple NAND pages. A sudden crash during checkpoint generation can leave partially programmed pages. Storing an IEEE 802.3 32-bit CRC over the full serialized payload ensures that a corrupted or truncated checkpoint file is detected and rejected during reboot, preventing catastrophic recovery state corruption.

### 17. How do you choose checkpoint frequency?
Checkpoint frequency balances **runtime write overhead** against **recovery time objective (RTO)**:
- **Too Frequent** (e.g., every 10 ops): Generates excessive internal metadata writes, degrading WAF, consuming NAND endurance, and causing latency spikes.
- **Too Infrequent** (e.g., every 100,000 ops): The WAL grows excessively long, requiring extensive replay time during SSD boot and consuming excessive spare flash blocks for logging.
A standard trade-off commits checkpoints every $N$ operations (e.g., 1,000–5,000 ops) or when the WAL approaches a fixed block threshold, followed by WAL truncation.

### 18. How do you recover after a crash during GC?
GC relocates data between blocks. To guarantee crash recovery:
1. Valid pages are programmed into the destination block.
2. A WAL entry of type `GC_RELOCATE` `{lba, old_ppa, new_ppa}` is committed.
3. Only after the relocation record is committed is the old page marked invalid.
4. If a crash occurs before the victim block is erased, recovery replays the WAL: if the record committed, the new page is recognized; if not, the original page remains valid in the source block. The erase operation is transactional.

### 19. What are the limitations of this simulator versus a real SSD?
- **Simplified Single-Die/Plane Model**: Real enterprise SSDs manage 8–16 channels with 4–8 dies per channel, plane-level interleaving, and superblocks striping across dies.
- **Synchronous Host Interface**: Real NVMe controllers process concurrent I/O queues (Submission/Completion Queue pairs) asynchronously with out-of-order execution.
- **Physical NAND Cell Characteristics**: Does not simulate read disturb, charge leakage, retention drift, temperature effects, or LDPC soft-decision decoding iterations.

### 20. How did deterministic seeds make debugging easier?
By coupling an explicit pseudo-random generator (SplitMix64) across workload generation, crash point injection, and scheduling:
- Any failing invariant violation or crash recovery mismatch is 100% reproducible on demand.
- A bug discovered on seed 27 can be stepped through line-by-line in GDB or LLDB with identical memory layouts, PPA sequences, and crash timings.

### 21. What invariants caught the corruption?
The simulator evaluates two invariant classes:
1. **Structural Invariants**:
   - `L2P_P2L_Bijective`: Every mapped LBA $L \to P$ must have $\text{P2L}[P] = L$.
   - `UniqueOwnership`: No physical page can be mapped to more than one LBA.
   - `FreePageConsistency`: Free pages must have page state `Free` and invalid LBA owner.
   - `BlockAccounting`: The sum of free, valid, and invalid pages in a block must exactly equal `pages_per_block`.
2. **Durability Invariants**:
   - `AcknowledgedWritesSurvive`: For every host-acknowledged write, reading that LBA after crash recovery must return the identical payload and CRC written.

### 22. How do TRIM commands affect mapping and GC?
A host TRIM (NVMe Dataset Management Deallocate) command notifies the FTL that a range of LBAs no longer contains valid file system data. The FTL:
1. Clears the L2P mapping entry ($\text{L2P}[L] \leftarrow \text{kInvalidPpa}$).
2. Marks the previous physical page as `Invalid` in page state tracking.
3. Does not write any NAND data.
This directly decreases the number of valid pages on the physical block, reducing future GC relocation work and lowering write amplification.

### 23. How do you model NAND latency?
Physical flash timing is modeled by aggregating operation times:
$$t_{\text{total}} = N_{\text{read}} \cdot t_{\text{READ}} + N_{\text{prog}} \cdot t_{\text{PROG}} + N_{\text{erase}} \cdot t_{\text{ERASE}} + \sum \Delta_{\text{jitter}}$$
Realistic synthetic values ($t_{\text{READ}} = 50\mu\text{s}$, $t_{\text{PROG}} = 600\mu\text{s}$, $t_{\text{ERASE}} = 3500\mu\text{s}$) accurately reflect that physical erases dominate time budgets by orders of magnitude.

### 24. How would multiple channels change the design?
In a multi-channel architecture:
1. **Channel Striping**: LBAs are interleaved across channels (e.g., `channel = LBA % num_channels`) to maximize bus throughput and parallelism.
2. **Superblocks**: Blocks across dies and channels are grouped into superblocks; erase and program operations are issued in lockstep across channels.
3. **Channel-Independent WAL**: Logging and checkpoints must either be striped across channels or managed per-channel to avoid bottlenecking concurrent command processing.

### 25. How would you extend this to Power-Loss Protection (PLP) semantics?
Enterprise SSDs feature hardware Power-Loss Protection capacitors (hold-up capacitors) providing 10–50ms of auxiliary power upon VCC rail drop. To model PLP:
1. On power-loss trigger, the controller transitions to emergency flush state.
2. The FTL writes volatile write buffers and dirty L2P cache entries into a pre-reserved, single-level cell (SLC) emergency log block.
3. Invariant checking verifies that data in volatile write buffers at the instant of power failure is successfully committed before capacitor voltage drops below operational thresholds.
